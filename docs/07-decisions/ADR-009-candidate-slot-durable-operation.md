# ADR-009：每个候选槽位复用一个持久操作

| 属性 | 值 |
|---|---|
| 状态 | accepted |
| 日期 | 2026-08-06 |

## 背景

一次已批准的创意方向可要求多个候选结果。Provider 可能同步返回图片，也可能先返回任务身份；Worker
可能在请求发出、响应丢失、结果下载、对象写入或数据库提交前后中断。若生成批次只拥有一个粗粒度 Job，
部分成功会迫使整个批次重试；若 Provider Attempt 自建状态机，则会与现有持久操作的 Lease、执行/对账
预算、不可覆盖 Provider Request ID、死信重放和恢复代次重复并产生双重权威。

## 决策

- 生成批次按精确 `candidate_count` 建立连续、稳定的候选槽位；每个槽位恰好拥有一个
  `IMAGE_GENERATION` 或 `IMAGE_EDITING` 持久操作。
- 槽位的逻辑身份由批次、槽位序号、已授权输入与策略版本确定；普通消息重放、Worker 重启和 Provider
  查询始终回到同一槽位与持久操作。
- Provider Attempt、路由切换和查询是该持久操作的追加执行历史，不是并行 Job 聚合。第一个已接受的
  Provider Request/Task ID 不可覆盖；未知结果只能对账，不能重新提交。
- 一个槽位只有在输出字节验证、受控对象持久化、任务资产版本、候选图片、用量、审计、事件和持久操作
  成功事实收敛后才可用。批次可展示部分进度，但不会把部分数据库/对象事实暴露为候选图片。
- 确认的可重试失败只能使用原模型路由决定中的兼容后备；内容/策略/权利拒绝和未知结果禁止切换。

## 后果

- 多候选部分成功可以独立恢复，失败槽位不会重复已经成功或可能已提交的付费调用。
- 现有 Worker、队列消费、Operation Executor、Lease、Reconciliation、DLQ 与审计接缝得到复用；Phase 4
  只新增生成领域事实和专属执行器，不新增通用任务框架。
- 记录数量按候选数增长，并要求批次读取聚合多个槽位；作为交换，每一次外部付费副作用都有独立、稳定、
  可对账的业务身份。
- 不提供查询语义的同步 Provider 在 unknown outcome 后会进入 operator wait，而不是牺牲至多一次有效结果
  约束去换取自动恢复。

## 验证

- 重复命令和消息只能得到原批次、槽位、持久操作、候选图片和用量身份。
- 在 Provider 调用、响应、对象写入和结果事务前后注入崩溃，证明不会重复已确认或未知的外部提交。
- 多候选中的成功、失败、对账和取消相互隔离，同时遵守批次的方案、权利、预算与保留边界。
- Kuaipao 同步 unknown outcome 进入 operator wait；Wan async task 使用精确 task ID 查询并收敛。
